Mapping NCA cybersecurity controls to Kubernetes

Compliance · 3 min read · Elifai engineering team · 8 November 2026

Most Saudi compliance teams know the NCA control documents well. Most platform teams know Kubernetes well. The gap is in between: which cluster setting proves which control, and where the evidence comes from. This guide shows how we close that gap on OpenShift, GKE, EKS and OKE.

Start from the control domains, not the tools

The Essential Cybersecurity Controls (ECC-2:2024) are organised into domains covering governance, defence, resilience, third-party and cloud security, and industrial systems. The Cloud Cybersecurity Controls (CCC-2:2024) add requirements for cloud providers and for organisations that use them. Rather than starting with a list of Kubernetes features, we start with the domains that touch a platform and ask, for each one, what an auditor will ask to see.

A working map

Control areaWhat we configureEvidence we hand over
Identity and access managementSSO to the cluster through your identity provider, role-based access per namespace, no shared admin accounts, short-lived credentialsRBAC export, access review records, login audit logs
Data protection and cryptographyEncryption at rest with customer-managed keys, TLS everywhere, secrets in Vault or a cloud KMS rather than plain Kubernetes secretsKey policy, certificate inventory, secret-store configuration
Vulnerability and patch managementImage scanning in the pipeline, signed images only, scheduled node and OS patching for RHEL or Ubuntu workersScan reports, admission-policy logs, patch compliance dashboard
Event logging and monitoringAPI server audit logging, central log retention in-Kingdom, alerting into a staffed operations centreRetention settings, sample alerts, incident tickets
Configuration and change managementAll cluster state in Git, changes through pull requests, policy-as-code (OPA Gatekeeper or Kyverno) blocking unsafe workloadsGit history, approval records, policy reports
Resilience and backupMulti-zone control plane, Velero or native backups stored in-Kingdom, restore tests on a scheduleBackup job history, signed restore-test results
Third-party and cloud securityDocumented shared-responsibility split with the cloud provider and with us as managed-service partnerResponsibility matrix, provider attestations

Exact control numbers differ between document versions and between ECC and CCC, so we keep the mapping in a spreadsheet tied to the version your regulator expects, and update it when NCA publishes a revision.

Make the evidence automatic

The expensive part of compliance is collecting evidence by hand before every audit. We avoid that by producing evidence as a side effect of running the platform: policy reports from the admission controller, patch status from the fleet dashboard, backup and restore results from scheduled jobs, and access reviews from the identity provider. A quarterly export then becomes a pack your compliance team can submit as it is.

Common gaps we find

  • Cluster-admin rights shared by a whole team, with no record of who did what.
  • Audit logs enabled but shipped to a region outside the Kingdom by default.
  • Backups that exist but have never been restored.
  • Kubernetes secrets stored in Git with base64 encoding mistaken for encryption.
